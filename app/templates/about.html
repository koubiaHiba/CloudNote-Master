Architecture

CloudNotes runs inside a Docker container hosted on Azure App Service. Every time code is pushed to the main branch on GitHub, a GitHub Actions workflow automatically builds a new container image, pushes it to Azure Container Registry, and deploys the updated image to App Service — with zero manual steps.

Cloud Services Used

  • Azure App Service Managed platform that runs the Docker container and exposes it over HTTPS on a public URL.
  • Azure Container Registry (ACR) Private Docker registry that stores and versions every container image built by the pipeline.
  • Azure Monitor Alerting rules watch for HTTP 5xx errors and high response times, notifying on any degradation.
  • GitHub Actions CI/CD automation: installs dependencies, runs the test suite, builds and pushes the image, then triggers deployment — all on every push to main.

Skills Demonstrated

Containerization

Multi-stage Dockerfile produces a minimal Python 3.11 image. The app is served by Gunicorn with 4 workers for production-grade concurrency.

CI/CD Pipeline

GitHub Actions workflow builds, tests, and deploys on every push. No manual intervention required after initial setup.

Cloud Deployment

Application deployed to Microsoft Azure App Service with a public HTTPS endpoint, configured to pull images directly from ACR.

Health Monitoring

A /health endpoint enables Azure App Service health checks. Azure Monitor alerts fire on HTTP 5xx errors or response times above 5 seconds.

Infrastructure as Code

All Azure resources can be reproduced from the Azure CLI commands in DEPLOYMENT_GUIDE.md — no clicking through the portal required.

Security Practices

Credentials are stored as encrypted GitHub Secrets, never in source code. ACR admin credentials are scoped to the deployment service principal.

Observability

CloudNotes is instrumented end-to-end so that every request leaves a trace in Azure and the app's internal state is always visible.

  • Structured JSON Logging Every request emits a single-line JSON object (timestamp, method, path, status, response time, request ID). Azure Log Analytics ingests these automatically, enabling queries like | where status == 500 or | summarize avg(response_time_ms) without any log-parsing configuration.
  • Custom Metrics Endpoint (/metrics) Returns a live JSON snapshot: total requests, requests by method and status code, notes created/deleted, average response time, uptime, and current note count. Any monitoring tool — or just curl — can poll this endpoint to confirm the app is alive and active.
  • Live Dashboard (/dashboard) A browser-based operations dashboard that auto-refreshes every 5 seconds. Shows all metrics in card layout, a pure-CSS bar chart of requests by HTTP method, and a rolling activity log of the last 10 requests with method, path, status, and response time.
  • Enhanced Health Check (/health) Returns a rich payload including app version, uptime, memory usage, note count, total requests served, Python version, and flags indicating whether the app is running in a container or on Azure App Service. Azure uses this endpoint to determine container health and restart the container if it returns a non-2xx response.
